OKR tracking module: secure evidence upload

A team capstone for the sponsor Micromax Technology. I built the part that checks every file a user attaches as evidence, and the review flow around it.

Project
OKR tracking module added to a sponsor's dashboard. Final-year capstone (CSIT321), Mar 2026 to present.
My part
The backend and admin side: role-based permissions for groups and managers, and the evidence upload feature for key results, including the scanner.
Stack
Node.js, Express, MongoDB, React, Socket.IO. Tested with Node's test runner and Cypress.
Code
Team repository (a stripped-down extract) and my commits

01 / problem

Why uploads need checking

The OKR module lets people attach evidence, such as a PDF or a spreadsheet, to a key result. Accepting files from users is a classic way to bring a malicious file into a company. It has its own entry, CWE-434, unrestricted upload of file with dangerous type, and the OWASP File Upload Cheat Sheet gives the standard advice: check the content and not only the file name, and limit the file size.

The goal was a feature that blocks the common malicious uploads, tells a manager when something was blocked, and keeps a record, without making honest users fight the system.

02 / flow

How an upload is handled

Four steps, in this order. A threat that cannot be approved is blocked before the slower checks run.

  1. Rate limit

    30 uploads per 5 minutes for each user, or for each IP address if there is no user. Past that, the server answers 429 with a Retry-After header.

  2. Built-in checks

    The real type of the file is sniffed from its bytes, then the checks for that type run. Some findings are final blocks straight away.

  3. Virus engine

    If a ClamAV server is configured, the file is streamed to it as well. In my setup it is optional.

  4. Decide and record

    Clean files are saved in a database transaction. A blocked file creates a report, alerts the managers and appears on the audit page.

03 / checks

What the scanner looks for

final block nobody can approve it. can be reviewed a manager can allow that exact file once.

Test files and programs

The EICAR test string is blocked on sight, and so is anything that starts like a Windows program (the DOS stub).

final block

ZIP and Office files

Covers .zip, .docx, .xlsx, .pptx and the Open Document formats. An archive is blocked for a declared unpacked size over 100 MB, a compression ratio over 500 on a large entry (a zip bomb), ZIP64 files, and unsafe paths such as absolute paths or "..". The start of each entry is checked for the EICAR string and for program headers (ELF, Mach-O, Java class, shebang, Windows PE).

final block

Risky content inside archives

Dangerous file extensions, Office and Open Document macros (vbaProject.bin, Scripts and Basic folders), nested archives and encrypted entries are flagged for a manager to look at.

can be reviewed

PDF

The file is searched for /JavaScript, /Launch, /EmbeddedFile and /RichMedia. Names hidden with #xx escapes are decoded, and compressed object streams are inflated first (4 MB per stream, 8 MB in total) so nothing hides inside them. Scripts, launch actions and embedded files can go to a manager. Other findings are final.

can be reviewed

Images

PNG, JPEG, GIF, WebP and HEIC files are checked for hidden script text (<?php, <script, <%@ page), a ZIP hidden inside the image, and more than 16 trailing bytes after a PNG ends.

final block

Other documents

Old Office files (.doc, .xls, .ppt) are checked for a VBA macro marker, and RTF files for embedded objects. CSV files are checked for cells that start with = + - or @ and then call cmd, powershell, mshta, rundll32, regsvr32, wscript, cscript, msexcel or dde, the classic CSV formula trick.

can be reviewed

What gets recorded and shown

Every upload gets a SHA-256 hash, a sniffed file type, the first bytes in hex and a text preview. The preview strips control and bidirectional characters so it cannot be used to disguise text. Virus signature names are cleaned to letters, numbers and a few symbols (80 characters at most) before they are shown.

04 / review

The review flow

When a file is blocked, someone responsible can look at it, and the decision is recorded.

  • Managers are the objective owner, the sender's supervisor and the group manager, with admins as the fallback.
  • A blocked upload creates a report and sends a live alert. Viewing a report, deciding on it and opening the audit log each use their own signed token.
  • The sender cannot view or decide their own report.
  • Approving needs a typed confirmation. A final block returns 409 "This block is final", and a second decision returns 409 "Already decided". The first decision wins.
  • An approval lets that exact file through once: the same SHA-256 hash, the same key result and the same uploader, within 48 hours.
  • Blocked records are deleted after 14 days. Once a decision is made they are kept for 90 days for the audit page.
  • Repeated attempts escalate to admins: 5 tries with the same file, or 3 blocked files within 24 hours.

Small details that matter

  • Alert text is escaped before it goes into a message, and ids are checked with mongoose.isObjectIdOrHexString before any lookup.
  • An approval is claimed with one atomic update (findOneAndUpdate to "used"), so two requests cannot spend the same approval.
  • If the database save fails after an approval was used, the approval is released again.
  • With CLAMAV_REQUIRED=true the upload fails closed with a 503 when the engine cannot be reached.

06 / tests

How it is tested

The backend tests use Node's built-in runner (node --test). They cover the scanner checks (evidenceScanner.test.js), the virus engine client (virusEngine.test.js), the blocked-upload report flow (blockedUploadReport.test.js) and an integration test of the backend (integration/backend.test.js). The frontend has Cypress end-to-end tests.

07 / limits

What it does not do

Honest limits

  • The checks are patterns and heuristics. A clean result means nothing known was found, not that the file is safe.
  • ClamAV is optional. By default, if the engine errors, the upload carries on with the built-in checks only (fail open). Setting CLAMAV_REQUIRED=true makes it fail closed.
  • The rate limiter keeps its counts in memory. They reset when the server restarts and are not shared between processes.
  • An approval depends on a manager's judgment.
  • The public repository is a stripped-down extract with the Business Calendar module and the OKR module. The sponsor's own dashboard is not public, so I cannot show it.
