LayerLens

A small web app that shows a visitor what their browser and network connection reveal, and says where each detail came from and how far to trust it. A tool that looks things up about visitors is easy to misuse, so the design starts with its limits.

Project
Independent project, Nov 2026.
Stack
Node.js 22 or newer with no packages to install. Plain JavaScript, HTML and CSS in the browser. Docker for packaging and GitHub Actions for the tests.
Status
Tested, not deployed. 62 automated tests pass on Node.js 22 and 24.
Code
github.com/hamimabbu/layerlens. Public, MIT licence.

01 / problem

Why a lookup tool needs care

A website can read many details about a visitor's browser and connection. Most visitors never see them, and they are easy to over-read. A shared IP address or a network registration record describes a connection, not the person using it. LayerLens shows the details back to the visitor: a browser check in the tab, a connection check on the server and optional public-record lookups. Each result lists its source, the time and what it cannot prove.

A tool like this has risks of its own. If it can be told which address to look up, it becomes a way to probe other networks. If it trusts forwarding headers, a visitor can pretend to be somebody else. If it shows text from outside sources as HTML, a hostile record can run a script in the page. The threat model in the repository lists nine risks, each with the control that answers it and what is still untested.

02 / flow

How a public-record lookup is handled

  1. Consent

    The operator has to switch a source on, and it is off by default. The visitor then picks it and approves who will receive the address.

  2. Derive

    The server works out the address from the connection itself. There is no field for a target, and a request that names one is rejected.

  3. Gate

    Local, private and reserved addresses stop here. Only a public address can leave the server, and only to approved destinations.

  4. Show

    The answer is size limited, trimmed and shown as plain text, with its source, its time and what it cannot prove.

Results stay in the tab. There is no results database, no cookies and no analytics. The rate counters are hashed with a key that changes on restart and are removed within about a minute. A redacted export can be previewed before anything is shared, and reset clears the tab.

03 / controls

What keeps it from being misused

No arbitrary target

The address comes from the connection, never from the request. This avoids the server-side request forgery (SSRF) risk that a lookup tool usually has.

Trusted headers only

Forwarding and fingerprint headers count only when they come from a proxy the operator listed. Otherwise the socket address is used.

Outbound limits

Web lookups use HTTPS only, a fixed list of hosts, no redirects, a 256 KB response cap and a 5 second timeout.

Request limits

4 KB request bodies, JSON only, 20 calls per visitor per minute, and unfinished requests are closed after 10 seconds. IPv6 visitors share one allowance per /64 range.

Safe display

Text from the server is shown as text, never as HTML, and the content security policy allows no remote scripts.

Container setup

A Dockerfile and Compose file run it as a non-root user with a read-only filesystem and no extra capabilities. The port is published on loopback only. It was built and run once on Linux.

04 / tests

How it is tested

npm test runs 62 tests with Node's built-in test runner, and GitHub Actions runs them on Node.js 22 and 24 for every push. They cover every route and method, request size and content type rules, requests that try to name their own target, the per-visitor limit with a mocked clock, address classification against the IANA special-purpose registries, reverse DNS against a local fake DNS server, failing and slow lookup sources, redirects, and how the page handles answers it cannot read.

A second review of the code found real problems. Each one was fixed and now has a test:

  • A missing public file returned an empty 200 response instead of an error.
  • An IPv6 visitor could get a fresh request allowance by changing the end of their address. Allowances are now counted per /64 range.
  • Node only checks request timeouts every 30 seconds by default, so stalled connections stayed open. The check interval is now 1 second.
  • Some reserved ranges, such as Teredo and the benchmarking range, were treated as public.
  • LACNIC answers plain application/json with a 406, so every lookup for a Latin American address failed. Trying the live registries once found it.

The test record in the repository also lists browser, accessibility and attack-script checks. Those scripts are not committed, so that part is a record and not something the repository can reproduce.

05 / limits

What it does not do

Honest limits

  • It is not deployed anywhere. Publishing the code does not run it, and it still needs HTTPS and connection limits at the front before public use.
  • The optional TLS fingerprint diagnostic (JA3, JA4 and HTTP/2 through Fingerproxy) has not been run against real TLS traffic. Its server side is tested with fake headers.
  • Reverse DNS has only run against a local test DNS server. The registry and InternetDB lookups were tried live a handful of times, so their accuracy and availability are not measured.
  • The page was only tested in Chromium, and only automated accessibility checks were run. Firefox, Safari, real phones and screen readers are untested.
  • It does not identify anyone. A browser attribute pattern is not a unique identity, and an IP record describes a connection.
  • No independent security audit has been done.

Credit

MyIP and CreepJS were reference reading, and no code from them is included. Fingerproxy (Apache-2.0) is the optional TLS fingerprint integration and is not bundled. The sources list in the repository includes the OWASP SSRF Prevention Cheat Sheet, RFC 9224 for RDAP bootstrap data and RFC 6269 on shared IP addresses.
